# momo 인증·세션·저장소 기능명세서

| 항목 | 내용 |
| --- | --- |
| 문서명 | 인증·세션·저장소 기능명세서 |
| 대상 버전 | 현재 구현 기준 (`feature/dongjoon`) |
| 작성일 | 2026-08-20 |
| 범위 | **이미 구현·동작하는 기능만** 기술. 지도·모임·친구 등 미구현 제품 기능은 제외 |
| 관련 코드 | Flutter `lib/` · Express `momo_server/` |

본 문서는 기획서의 목표 범위가 아니라, **지금 앱과 서버가 실제로 제공하는 계약**을 고정한다. 구현과 불일치하면 코드를 우선한다.

---

## 1. 문서 목적

- 로그인, 로그아웃, 자동 로그인, 회원가입(OTP 포함), Firebase/DB, `momo_server`의 **완료된 동작**을 한곳에 정리한다.
- 프론트·백엔드·저장소 사이의 HTTP 계약, 검증 정책, 실패 코드를 검수·인수 기준으로 쓴다.
- 이후 자체 서버로 저장소만 교체할 때, **앱 API와 화면 흐름을 유지하기 위한 기준선**으로 쓴다.

## 2. 구현 범위 요약

### 2.1 완료 (본 명세서 대상)

| 구분 | 기능 |
| --- | --- |
| 가입 | 랜딩 → 이메일 OTP 발송 → OTP 검증 → 비밀번호 → 생년월일 → 닉네임 중복확인 → 가입 완료 → (가능하면) 자동 로그인 → 메인 |
| 로그인 | 이메일+비밀번호 → JWT 발급 → 기기 세션 저장 → 메인 |
| 자동 로그인 | 앱 기동 시 저장된 세션·만료시각 확인 후 메인 또는 랜딩 |
| 로그아웃 | 메인 화면 임시 버튼으로 세션 삭제 후 랜딩 |
| OTP | 6자리 생성, Gmail 발송, 5분 유효, 재전송 제한, 검증 후 가입 게이트 |
| 사용자 저장 | Firestore `users` (기본) / SQLite 롤백 |
| 서버 | Express `momo_server` HTTP API |

### 2.2 의도적으로 미구현 (본 문서 비대상)

| 항목 | 상태 |
| --- | --- |
| ID 찾기 (`findId`) | 도메인 메서드만 존재, 화면·API 없음 (`not-implemented`) |
| 비밀번호 변경 (`changePassword`) | 동일 |
| Firebase Authentication (비밀번호 계정) | 사용하지 않음. 비밀번호는 서버 bcrypt |
| 앱의 Firestore 직접 읽기/쓰기 | 사용하지 않음. 앱은 HTTP만 |
| 모임·지도·친구·채팅 | 미구현 |

## 3. 아키텍처

```
Flutter 앱
  ├─ AuthRepository (도메인 인터페이스)
  ├─ EmailOtpAuthRepository  ──HTTP──►  momo_server (Express)
  ├─ SessionStore (SharedPreferences)
  └─ Firebase.initializeApp  (앱 기동용. 인증 데이터 경로 아님)

momo_server
  ├─ OTP: 프로세스 메모리 Map + Nodemailer(Gmail)
  ├─ Auth: bcrypt + JWT
  └─ userService
        ├─ STORAGE=firestore → Firebase Admin → Firestore users
        └─ STORAGE=sqlite    → better-sqlite3 → data/momo.db
```

**원칙**

1. 화면은 `AuthRepository`만 의존한다. HTTP·Firebase·SQLite를 화면에서 직접 호출하지 않는다.
2. 사용자 계정은 **서버 뒤 저장소**에만 둔다. Flutter는 Admin SDK / 클라이언트 Firestore를 쓰지 않는다.
3. OTP는 DB에 저장하지 않는다. 서버 프로세스 메모리이며, 재시작 시 사라진다.
4. 비밀번호는 **평문 저장 금지**. bcrypt 해시만 저장한다.

## 4. 정책·검증 규칙

프론트(`lib/core/constants.dart`)에서 1차 검증하고, 서버(`authRoutes.js`)에서 재검증한다. 값이 다르면 **서버가 최종 권한**을 갖는다.

| 항목 | 프론트 | 서버 |
| --- | --- | --- |
| 이메일 | RFC 단순화 정규식, trim | 동일 계열 정규식 |
| 비밀번호 | 영문 1자 이상 + 숫자 1자 이상, 특수문자 허용, 공백 불가, 8~32자 | **최소 8자만** 검사 (문자 종류·상한은 서버에 없음) |
| OTP | 숫자 6자리 | 서버가 생성한 문자열과 완전 일치 |
| OTP 유효 | UI 타이머 5분 | 서버 5분 (`OTP_VALIDITY_MS`) |
| OTP 재전송 | UI 쿨다운 30초 | 서버 **60초** (`RESEND_LIMIT_MS`) |
| 닉네임 | 2~10자 (trim 후 길이) | 동일 |
| 생년월일 | 올해−100 ~ 올해, 유효한 달력 날짜 | `YYYY-MM-DD` 형식만 검사 |
| 이메일/닉네임 유니크 | 서버 조회 | Firestore: `emailLower` / `nicknameLower` 쿼리. SQLite: `UNIQUE COLLATE NOCASE` |

**불일치 주의:** OTP 재전송 쿨다운이 프론트 30초·서버 60초이다. UI에서 재전송이 열려도 서버가 429를 줄 수 있다.

## 5. 클라이언트 화면·흐름

### 5.1 화면 목록 (인증 관련)

| ID | 화면 | 파일 | 역할 |
| --- | --- | --- | --- |
| S-LANDING | 랜딩 | `login_screen.dart` | 시작하기 / 계정이 이미 있습니다 |
| S-EMAIL | 이메일 | `email_input_screen.dart` | OTP 발송 |
| S-OTP | OTP | `otp_input_screen.dart` | 6자리 입력·재전송·확인 |
| S-PW | 비밀번호 | `password_setup_screen.dart` | 설정·확인 일치·정책 |
| S-BIRTH | 생년월일 | `birthdate_input_screen.dart` | 휠+직접 입력 |
| S-NICK | 닉네임 | `nickname_setup_screen.dart` | 중복확인·가입 완료 |
| S-LOGIN | 로그인 | `login_form_screen.dart` | 이메일+비밀번호 |
| S-MAIN | 메인 | `main_screen.dart` | 플레이스홀더 + 임시 로그아웃 |

진입 시 기본 구현체는 `EmailOtpAuthRepository`이다. 가입 중간 화면은 같은 인스턴스를 생성자로 전달한다.

### 5.2 회원가입 시나리오

```
S-LANDING --[시작하기]--> S-EMAIL --[계속 / sendOtp]--> S-OTP
  --[확인 / verifyOtp]--> S-PW --[계속]--> S-BIRTH --[계속]--> S-NICK
  --[가입 완료 / completeSignUp]--> (login + SessionStore.save) --> S-MAIN
```

| 단계 | 동작 | 성공 | 실패 |
| --- | --- | --- | --- |
| 이메일 | 형식 유효 시 `sendOtp(signUp)` | OTP 화면, 만료시각 전달 | SnackBar (`AuthException.message`) |
| OTP | 6자리 확인, 유효시간·재전송 UI | `VerificationToken` 보유 후 비밀번호 화면 | 빨간 테두리·입력 초기화 (`otp-invalid` 등) |
| 비밀번호 | 정책 + 확인 일치 시에만 계속 | 생년월일 화면으로 평문 비밀번호 전달 | 버튼 비활성, 정책/불일치 문구 |
| 생년월일 | 휠/텍스트 동기화, 일(day) clamp | `DateTime` 전달 | 유효하지 않으면 계속 비활성 |
| 닉네임 | `checkNicknameAvailability` 성공한 문자열과 입력이 같을 때만 가입 | `completeSignUp` | 중복 시 빨간 문구, 가입 비활성 |
| 가입 후 | 동일 email/password로 `login` → `SessionStore.save` | 메인, 스택 제거 (`pushAndRemoveUntil`) | **로그인 실패해도 가입은 성공으로 보고 메인 진입** |

`completeSignUp`에 넘기는 `verificationToken`은 앱이 들고 있지만, **현재 서버 `/signup`은 이 토큰을 받지 않는다.** 서버는 OTP 메모리의 `verified` 플래그만 본다.

### 5.3 로그인 시나리오

```
S-LANDING --[계정이 이미 있습니다]--> S-LOGIN --[로그인]--> S-MAIN
```

- 이메일이 정규식에 맞고 비밀번호가 비어 있지 않으면 제출 가능.
- 성공: JWT를 `AuthSession`으로 매핑, `SessionStore.save`, 메인으로 스택 제거.
- 실패: SnackBar. 계정 존재 여부는 메시지로 구분하지 않음 (서버와 동일).

클라이언트 `AuthSession.accessTokenExpiresAt`은 JWT의 `exp`를 파싱하지 않고, **로그인 시각 + 7일**로 넣는다 (`EmailOtpAuthRepository.login`). 서버 JWT 만료(`JWT_EXPIRES_IN`, 기본 `7d`)와 맞추려는 값이다.

### 5.4 자동 로그인

앱 진입: `main.dart` → `Firebase.initializeApp` → `_AppEntry`.

1. `SessionStore.read()`
2. 세션이 있고 `accessTokenExpiresAt`이 **현재 UTC보다 이후**이면 `MainScreen`
3. 없거나 만료이면 `LoginScreen`
4. 읽기 전: 로딩 스피너

서버에 토큰을 재검증하지 않는다. **로컬 만료시각만** 본다. 만료된 세션은 메인에 넣지 않지만, SharedPreferences 값은 자동 삭제하지 않는다 (다음 로그인 시 덮어씀).

### 5.5 로그아웃

`MainScreen` 우측 상단 **로그아웃**(디버그용).

1. `SessionStore.clear()` — 키 `auth_session` 제거
2. `LoginScreen`으로 `pushAndRemoveUntil` (전체 스택 제거)

서버 측 토큰 무효화(블랙리스트)는 없다. 클라이언트가 JWT를 버리면 이후 API에 실어 보내지 않는 구조이며, 현재 인증 이후 보호 API도 없다.

## 6. 세션 저장 (`SessionStore`)

| 항목 | 내용 |
| --- | --- |
| 구현 | `lib/data/session_store.dart` |
| 저장소 | `SharedPreferences` (평문 JSON). 운영 시 secure storage 교체 권장 |
| 키 | `auth_session` |
| 필드 | `userId`, `nickname`, `accessToken`, `refreshToken`, `accessTokenExpiresAt` (ISO-8601) |
| `userId` | 서버 `user.id`가 아니라 **로그인 응답의 email**을 넣는 구현 (`EmailOtpAuthRepository`) |
| `refreshToken` | 서버가 발급하지 않음. 항상 null |
| 파손 데이터 | `read()` 시 파싱 실패하면 키 삭제 후 null |

메서드: `save` / `read` / `clear` / `hasValidSession`.

## 7. momo_server HTTP API

기본 URL

| 클라이언트 | Base URL |
| --- | --- |
| Android 에뮬레이터 | `http://10.0.2.2:3000` |
| 그 외 (iOS 시뮬, 데스크톱, 웹) | `http://localhost:3000` |
| 타임아웃 | 10초 |

공통: JSON, CORS 허용, 비밀번호는 서버 로그에서 `***` 마스킹.

헬스: `GET /` → `OTP server is running (storage=firestore|sqlite)`

### 7.1 `POST /send-email-otp`

**요청**

```json
{ "email": "user@example.com" }
```

**처리**

1. `email` 필수.
2. 같은 이메일로 마지막 발송 후 60초 미만이면 429.
3. 100000~999999 정수 문자열 OTP 생성, 메모리 저장, 만료 = now+5분, `verified=false`.
4. Gmail로 발송. 제목 `회원가입 인증번호`, 본문 `인증번호는 {otp} 입니다. 5분 안에 입력해주세요.`

**응답**

| 상태 | 본문 |
| --- | --- |
| 200 | `{ success: true, message: "OTP sent successfully" }` |
| 400 | email 없음 |
| 429 | `{ success: false, message: "Too many requests", error: "RESEND_LIMIT" }` |
| 500 | 메일/서버 오류 |

가입 여부(`email-already-used`)는 **검사하지 않는다.** 이미 가입된 이메일도 OTP를 받을 수 있다. 중복은 `/signup`에서 409.

### 7.2 `POST /verify-email-otp`

**요청**

```json
{ "email": "user@example.com", "code": "123456" }
```

**처리**

| 조건 | 상태 | message |
| --- | --- | --- |
| 저장된 OTP 없음 | 404 | `OTP not found` |
| 이미 verified | 400 | `Already verified` |
| 만료 | 400 | `OTP expired` (항목 삭제) |
| 코드 불일치 | 401 | `Wrong OTP` (항목 유지, 시도 횟수 제한 없음) |
| 일치 | 200 | `Email verified successfully` — OTP 값 제거, `verified=true` |

성공 후에도 가입 전까지 메모리에 `verified`가 남는다. `/signup`이 `isEmailVerified`로 확인한다.

### 7.3 `GET /check-nickname?nickname=`

| 상태 | 의미 |
| --- | --- |
| 400 | 파라미터 없음 또는 길이 2~10 위반. `available: false` |
| 200 | `available: true/false`, 안내 메시지 |
| 500 | 저장소 오류 |

### 7.4 `POST /signup`

**요청**

```json
{
  "email": "user@example.com",
  "password": "Abcd1234!",
  "nickname": "모모",
  "birthdate": "2003-03-26"
}
```

`verificationToken`은 받지 않는다.

**가드 순서:** 필수값 → 이메일 형식 → 비밀번호 길이≥8 → 닉네임 길이 → 생년월일 형식 → **OTP verified** → 이메일 중복 → 닉네임 중복 → bcrypt(rounds=10) → 사용자 생성 → OTP 메모리 삭제.

**응답**

| 상태 | 의미 |
| --- | --- |
| 201 | `{ success: true, message: "회원가입이 완료되었습니다.", userId }` |
| 400 | 검증 실패 |
| 403 | `이메일 인증이 필요합니다.` |
| 409 | 이메일 또는 닉네임 중복 |
| 500 | 서버 오류 |

`userId`는 Firestore 문서 ID 또는 SQLite `lastInsertRowid`.

### 7.5 `POST /login`

**요청**

```json
{ "email": "user@example.com", "password": "..." }
```

계정 없음과 비밀번호 불일치는 모두 **401** + `이메일 또는 비밀번호가 올바르지 않습니다.` (열거 방지).

**성공 200**

```json
{
  "success": true,
  "message": "로그인 되었습니다.",
  "token": "<JWT>",
  "user": { "id": "<userId>", "email": "...", "nickname": "..." }
}
```

JWT payload: `{ sub: user.id, email: user.email }`, 서명 `JWT_SECRET`, 만료 `JWT_EXPIRES_IN` (기본 7d).

## 8. OTP 상세 (서버 메모리)

구현: `momo_server/services/otpService.js`

| 항목 | 값 |
| --- | --- |
| 저장 | `Map` 키 = 요청 `email` 문자열 (정규화 없음. 대소문자 다른 주소는 별도 키) |
| 생성 | `Math.floor(100000 + Math.random() * 900000)` |
| 유효 | 5분 |
| 재전송 | 동일 키 기준 60초 |
| 검증 성공 | `otp`를 null로, `verified=true` |
| 가입 후 | `clearOtpForEmail`로 삭제 |

**한계 (명시)**

- 서버 재시작 시 모든 OTP·verified 상태 소실 → 가입 중이던 사용자는 OTP를 다시 받아야 한다.
- 다중 인스턴스(로드밸런서)에서는 인스턴스마다 Map이 달라 동작하지 않는다.
- 시도 횟수 제한(`otp-attempts`)은 **미구현**. 만료 전까지 무한 재시도 가능.
- 도메인의 `OtpPurpose`(비밀번호 변경·ID 찾기)는 서버가 구분하지 않는다. 발송 API는 가입 메일 문구만 사용.

프론트 OTP 화면: 유효시간 카운트다운, 재전송 30초 UI, 오류 시 빨간 테두리·입력 클리어.

## 9. 사용자 저장소

### 9.1 전환 스위치

환경변수 `STORAGE` (`firestore` 기본, `sqlite` 롤백).

파사드: `momo_server/services/userService.js`  
메서드: `findByEmail` / `isNicknameTaken` / `createUser` / `listUsersForExport`

`findByEmail` 반환 shape (양쪽 동일):

```
{ id, email, password_hash, nickname, birthdate, created_at }
```

### 9.2 Firestore (기본)

- Admin SDK (`momo_server/firebase.js`). 서비스 계정 JSON + `FIREBASE_PROJECT_ID`.
- 컬렉션 `users`, 문서 ID 자동 생성.
- 앱은 Firestore에 직접 쓰지 않는다. 규칙상 **클라이언트 deny + Admin만**을 권장.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| email | string | 표시·로그인에 쓰는 원문(trim) |
| emailLower | string | 조회용 소문자 |
| passwordHash | string | bcrypt. export/조회 스크립트에서 제외 |
| nickname | string | trim |
| nicknameLower | string | 조회용 소문자 |
| birthdate | string | `YYYY-MM-DD` |
| createdAt | string (ISO) | 생성 시각 |
| legacySqliteId | number? | 마이그레이션 시에만 |

복합 유니크 인덱스는 없다. 가입 시 서버가 쿼리로 중복을 막는다. 동시 가입 레이스는 Firestore 제약으로 완벽히 막히지 않을 수 있다.

### 9.3 SQLite (롤백)

파일: `momo_server/data/momo.db` (gitignore). WAL 모드.

```
users (
  id INTEGER PK AUTOINCREMENT,
  email TEXT UNIQUE COLLATE NOCASE,
  password_hash TEXT NOT NULL,
  nickname TEXT UNIQUE COLLATE NOCASE,
  birthdate TEXT NOT NULL,
  created_at TEXT DEFAULT datetime('now')
)
```

### 9.4 마이그레이션·조회 스크립트

| npm script | 동작 |
| --- | --- |
| `db:migrate` | SQLite `users` → Firestore. 동일 `emailLower`면 skip. `createdAt`을 SQLite 값으로 맞춤 |
| `db:view` | 현재 `STORAGE` 사용자 목록 (해시 없음) |
| `db:export` | `data/export-users.json` — `id, email, nickname, birthdate, created_at` |
| `smoke:store` | find/nickname/bcrypt 형식 스모크 |

AI 학습용 추출은 **passwordHash를 절대 포함하지 않는다.**

## 10. Firebase (앱 vs 서버)

| 계층 | 역할 |
| --- | --- |
| Flutter `Firebase.initializeApp` | 기동 시 초기화 (`WidgetsFlutterBinding.ensureInitialized` 이후). **로그인/가입 데이터 경로가 아님** |
| Flutter `firebase_options.dart` / `google-services.json` | FlutterFire 설정 산출물 |
| 서버 Admin + Firestore | 실제 사용자 레코드 CRUD |
| Firebase Auth | **미사용**. 비밀번호 검증은 bcrypt+JWT |

Cloud Firestore API가 프로젝트에서 비활성이면 `db:view` 등이 `SERVICE_DISABLED`로 실패한다. 콘솔에서 Firestore DB 생성 및 API 활성화가 선행 조건이다.

## 13. 검수 체크리스트 (완료 기능)

- [ ] 유효 이메일로 OTP 메일 수신, 6자리 입력 시 비밀번호 화면 진입
- [ ] 잘못된 OTP → 오류 UI, 재시도 가능
- [ ] 만료 후 확인 → 실패, 재전송 후 성공
- [ ] 재전송을 서버 60초 안에 연속 요청 → 429 / 앱 안내
- [ ] 비밀번호: 영문+숫자 8자+, 특수문자 포함 시 계속 가능, 불일치 시 불가
- [ ] 닉네임 중복 확인 후 가입, 미확인·수정 시 가입 버튼 비활성
- [ ] OTP 없이 `/signup` 직접 호출 → 403
- [ ] 가입 후 Firestore(또는 SQLite)에 해시만 저장, 평문 없음
- [ ] 로그인 성공 → 메인, 재실행 시 만료 전이면 메인(자동 로그인)
- [ ] 로그아웃 → 랜딩, 재실행 시 로그인 화면
- [ ] 잘못된 비밀번호 → 401 동일 메시지, 계정 열거 불가
- [ ] `db:export` JSON에 비밀번호/해시 없음

## 14. 알려진 구현 차이·후속 과제

본 명세는 현재 코드를 있는 그대로 적는다. 개선이 필요한 점은 아래와 같다.

1. OTP 재전송: 프론트 30초 vs 서버 60초.
2. `/signup`이 `verificationToken`을 받지 않음. 우회 방지는 동일 서버 프로세스의 메모리 `verified`에만 의존.
3. `AuthSession.userId`가 이메일이고, 서버 `user.id`와 다름.
4. JWT를 이후 API Authorization 헤더로 쓰지 않음 (보호 리소스 없음).
5. 로그아웃은 UI 디버그 버튼. 설정 메뉴 없음.
6. 서버 비밀번호 정책이 프론트보다 약함 (길이만).
7. `findId` / `changePassword` 미구현.
8. Flutter Firebase 초기화는 인증 저장 경로와 무관. 제거해도 Express 인증은 동작한다.
